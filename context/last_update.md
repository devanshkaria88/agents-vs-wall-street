**Yes:** the reader's behavior is entirely system-prompt-driven. Its prompt is assembled from the skill files (`method.md` + the company brief, whose **driver task list** is literally the reader's shopping list — one task per driver key, with where to look and expected units) plus whatever you type into SYSTEM PROMPT EXTRA in the config panel, which is appended verbatim. **No:** finding it doesn't mean it *does* anything. Whatever the reader submits flows through firewall → vote → **merge**, and merge only accepts keys that already exist in the pinned drivers file — anything else gets logged as `ignored — not a known driver key`. And even a key that survived merge only matters if an engine formula actually consumes it; the calculators are hand-written per metric. So a novel item dies twice: once at the merge contract, once by having no arithmetic that reads it.

That's deliberate — it's the barrier that stops prompt text (or an enthusiastic reader) from injecting arbitrary numbers into the deterministic engine. To genuinely add a new extraction item you'd touch three places: pin the key in `research/drivers/<company>.json`, let skillgen regenerate the brief (it rebuilds the task list from the pinned keys automatically), and give the engine a formula that uses it.

There *is* one sanctioned escape hatch: `additional_evidence`. The reader is told to report anything notable that falls outside its task list, and that channel surfaces in the merge report for review. That's exactly how the GMS find happened this morning — the readers flagged that the 10-Q contradicted our $1,975M inference, the divergence policy held the reviewed value, and adoption was a deliberate act (pin + formula change), not an automatic one.
