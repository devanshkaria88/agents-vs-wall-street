Exactly right — with two mechanical details that determine whether it works smoothly.

**The flow you described does work end-to-end for *extraction*:** skillgen reads the driver keys straight from `research/drivers/<company>.json` and its `submit_skill` guard *requires* every key to appear in the generated brief (it rejects the skill otherwise), so the skill-writer will research your new key and write a task for it — where to look, what unit, how to verify. The readers then resolve it like any other task, it passes the firewall and vote, and merge accepts it because the key now exists in pinned. You'd see the whole life of it: the searches in the event feed, the vote support, the merge decision, and it lands in the live drivers file with its citation. The validator agent would even get it in its review payload.

**Detail 1 — pin it as an `assumption` with a numeric placeholder, not null.** Merge's rule is: `assumption` kind gets *upgraded* by live extraction (that's the designed path for "I want the agent to find this"); `base`/`anchor` kinds mean "pinned wins, divergence logged." And the merge code does `float(value)` on non-assumption kinds, so a `null` value would crash the run. Shape it like:

```json
"total_sales_count": {
  "value": 0.0, "low": 0.0, "high": 0.0,
  "kind": "assumption", "unit": "USDm",
  "notes": "extract from latest 10-Q; agent upgrades this"
}
```

**Detail 2 — it will *show*, but it won't *do*.** Same boundary as before: the engine's calculators only read the keys their formulas name, so your new driver sits in the merged file, cited and voted, completely inert to the twelve numbers until you write a formula that consumes it. Harmless in the best way — extra keys are simply never read.
